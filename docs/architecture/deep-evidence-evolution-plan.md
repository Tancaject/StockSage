# Agent 自进化方案：统一进化内核 + FUNDAMENTALS / DEEP 两条线

状态：方案草案（2026-10-13），暂停，先完成[评测体系优化](eval-system-plan.md)的 S4～S6（统一评审、真实输出校准、题集）。用户要求两套 Agent 都进化，因此改为"统一内核 + 两条线"。
前置：[DEEP 取证循环](deep-react-plan.md)（M0～M5 已完成，默认开启）；[自进化调研](../reviews/2026-09-25-agent-self-evolution-research.md)；[FUNDAMENTALS 方法进化 V1](../evolution/evolution-v1-contract.md)。

## 为什么从 DEEP 先跑通内核

FUNDAMENTALS 方法进化的工程链路已经完整（失败池、分诊、反思、候选编译、两阶段回放、批准、灰度），但一次都没有改变过线上行为：

- `rollout=OFF`，没有已批准的方法包。
- 18 题对强模型偏容易，基线不犯错，学不到东西（见 progress 10-05 的 P0 结论）。原计划依赖真实用户反馈，但作品项目没有真实流量。
- 生产模型 10-13 换成了 deepseek-v4-pro-0813，旧基线和旧候选全部作废。

DEEP 取证循环更适合作为首个真正跑通的进化对象：

| | FUNDAMENTALS 方法 | DEEP 取证策略 |
|---|---|---|
| 学习信号 | 等真实失败反馈，稀缺 | 每次取证的 Trace 直接暴露缺口：哪个必需维度没覆盖、哪次检索跑偏、哪个工具返回为空 |
| 评测成本 | 两阶段回放，每题几毛到几元 | 只跑证据阶段（`stocksage.research.eval.evidence-only`），每题几分钱 |
| 评测指标 | 四维语义质量，依赖校准过的复核 | 必需维度的证据覆盖，更接近客观判定 |
| 可变对象 | 一段方法正文 | 带适用条件的取证经验，在工具菜单和校验规则不变的前提下影响模型选什么工具、搜什么主题 |

调研报告把"执行策略优化"排在后面，条件是"只在已有可选动作和预算内实验"。取证循环的工具菜单、参数校验和停止条件正好满足这个前提：经验只能改变模型在既定菜单内的选择，不能扩大权限。

FUNDAMENTALS 同样进化，但它卡在学习信号上，需要主动构造难题集（见"FUNDAMENTALS 线"）。两条线共用一个进化内核，DEEP 信号快、成本低，用来先验证内核。

## 统一进化内核

两条线共用以下部件，只在注入方式和评测器上分开：

| 部件 | 共用内容 | FUNDAMENTALS | DEEP 取证 |
|---|---|---|---|
| 经验记录 | 适用条件、做法、限制、来源、版本、状态；注册表；校验器（禁止公司名、ticker、数字） | | |
| 失败来源 | `evolution_failure_cases` 加 `target` 字段，统一分诊 | 用户反馈、BLOCKED/FAILED、难题集复现 | 维度缺口、Harness 缺口 |
| 反思生成 | 按主题批量生成，同义合并，已有经验优先修订 | | |
| 验收 | dev/holdout 配对对照，判定规则预先写定，允许"无改善" | | |
| 上线 | 批准包 + sha256，OFF/ALLOWLIST/ALL，Trace 记录选用 | | |
| 注入 | | 沿用 V1：经验编译进整段方法正文 | 最多 3 条匹配经验注入循环初始提示 |
| 评测器 | | 两阶段回答质量 + 数值确定性核验（已有） | 维度覆盖评审（新做） |

现有 Python 模块（`evolution_experiences`、`evolution_reflection`、`evolution_acceptance`、`evolution_failure_pool`、`evolution_release`）优先改成按 `target` 区分的通用实现，不另起一套；FUNDAMENTALS 现有的数据和历史结论不改写。

## 进化什么（DEEP 线）

**取证经验（evidence playbook entry）**，一条记录包含：

- `conditions`：适用条件，用确定性的题目主题标签表示，如 `deep-topic-antitrust`、`deep-topic-export-control`、`deep-topic-supply-chain`、`deep-topic-capex-fcf`、`deep-topic-cycle`、`deep-topic-competition`。标签由问题文本和标的类型按规则推导，不依赖模型判断。
- `guidance`：取证做法，不超过 300 字。例如："监管或诉讼类问题，先查 10-K Item 1A 和法律诉讼相关段落，确认披露口径；再用新闻搜索裁决、补救方案或上诉的最新进展，主题写案件名和'remedy/appeal'，不要只写公司名。"
- `limits`：不适用的情形。
- `provenance`：来源 Trace、触发它的缺口、父版本、状态（候选 / 已批准 / 已撤回）。

约束：

- 不得包含公司名、ticker、具体数字或结论，只写方法。由校验器检查，防止把某题的答案背下来。
- 只影响模型选择，不改工具菜单、参数校验、标的锁定和停止条件。
- 每次最多注入 3 条匹配的经验，避免提示词膨胀。

## 闭环

```
dev 题集 → 只跑证据阶段（基线） → 自动维度评审 → 缺口 + 取证轨迹
   → 反思生成经验候选 → 去重/校验 → dev 定向筛选
   → 冻结组合包 → holdout 对照（基线 vs 组合包） → 保留 / 修订 / 无改善
   → 批准 → ALLOWLIST 灰度 → 生产缺口回流（第二阶段）
```

## 实施拆解

| 步骤 | 内容 | 改动点 | 验收 |
|---|---|---|---|
| E1 题集 | `deep_react_cases.jsonl` 从 11 题扩到约 30 题，覆盖 6 类主题；每题 3 个必需维度，写清判定口径；按公司拆成 dev 约 15 题、holdout 约 15 题，holdout 的公司不出现在 dev 中 | `evals/` 数据文件和 schema 校验 | schema 校验通过；主题和单跳/多步分布表；dev 与 holdout 无公司重叠 |
| E2 自动维度评审 | 用 STRONG 模型逐维度判定 0/1/2，必须引用证据 ID 和原文片段。评审前统一证据名称（去掉 `loop*`、`focusedNewsSearch` 等组别痕迹），打乱顺序 | 新 `evals/deep_facet_judge.py`；证据摘要提供完整正文给评审 | 与人工判分对照（M5 的 12 份加新标的 12 份）：一致率和加权 κ 达到预先写定的门槛；不一致的题逐条列出原因；重复评审一致性 |
| E3 后端注入 | 加载已批准的取证经验包（JSON 加 sha256，沿用 approved-method 的方式）；按标签匹配；注入循环初始提示的"适用取证经验"段；Trace 记录 `playbookSelection`；`rollout=OFF/ALLOWLIST/ALL`；评测时可指定包 | `DeepEvidenceLoopService` 初始提示、新的小型注册类、配置项；主题标签推导 | OFF 时提示词逐字节不变；匹配和上限的单项检查（jshell）；sha 不符拒绝加载；Trace 字段可见 |
| E4 反思与注册表 | 按主题分组读取 dev 失败（缺口维度、评审理由、循环轨迹），批量提出经验；同义合并，已有经验优先修订；校验器拒绝含公司或数字的经验 | 新 `evals/deep_playbook.py`（注册、校验、编译包），复用 `eval_common` 的哈希 | 用 M5 已有轨迹离线生成，人工抽查经验可读、无泄题；校验器负例 |

## FUNDAMENTALS 线

卡点：基线不犯错，学不到东西；旧基线是 qwen3.8-max 跑的，已作废。

| 步骤 | 内容 | 验收 |
|---|---|---|
| F1 难题集 | 按 P0 确认在强模型上仍会出现的错误类出题：单季与累计期间混比、表内可算却称"缺失"、整合时丢失限定词、无限定的融资依赖推断。每类 3～5 题，用不同公司，拆成 dev/holdout | 每题有来源、必答项和标准答案；数值经确定性核验 |
| F2 deepseek 新基线 | 在现生产模型上跑两阶段基线，确认这些错误能复现 | 逐题列出复现情况；复现不了的错误类如实记为"当前模型不再犯"，不为学而学 |
| F3 接入内核 | 失败池、注册表、反思、验收、批准改用统一内核；方法选用条件随新模型重新绑定 | 与原 V1 选用检查的 20 项行为一致 |
| F4 一轮闭环 | 与 DEEP 的 E5 同样的流程和判定规则 | holdout 两阶段质量提升且必答完整性不退步，否则记"无改善" |

F1、F2 不依赖内核，可以与 DEEP 的 E1～E3 并行。

其他角色（Market/News 分析师、多空辩论、Manager）本轮不进化：每多一个对象就多一套需要先校准的评测器。两条线跑出可信数字后，再按同一内核扩展。

## 预算（按今天的实测估算）

- 只跑证据阶段：每次约 0.05 元，C 组约 40～60 秒。
- 自动评审：每份约 1 万 token 输入，按 deepseek 高峰价约 0.1 元。
- E5 holdout 对照：15 题 × 2 组 × 2 次 = 60 次运行加 60 次评审，约 9 元；dev 基线和筛选约 5～10 元。
- DEEP 一轮完整闭环合计 20～30 元。
- FUNDAMENTALS 两阶段回放每题约 0.3～0.6 元（两次 STANDARD 模型调用，带思考），F2 基线约 20 题 × 2 次，约 15～25 元；F4 闭环另计。
- 每次实际运行前先报题数和预估费用。

## 风险与对策

- **评审偏差**：模型评审有位置、长度和自偏好偏差。对策是人工校准、隐藏组别、打乱顺序；结论标注为 AI 评测，不冒充人工验收。
- **新闻检索不确定**：同题两次搜到的结果不同。对策是每题每组重复 2 次，报告波动。
- **对 dev 过拟合**：对策是 holdout 换公司，在 holdout 上不调参；修改后换新的确认题。
- **经验变成背答案**：对策是校验器禁止公司、ticker 和数字，并人工抽查。
- **提示词膨胀**：每次最多 3 条，每条最多 300 字。

## 不在本轮

- GEPA 等自动提示词搜索。
- 取证工具菜单本身的扩展。
- 关联实体扩展（deep-react-plan 的第二版）。
- 辩论和报告阶段的进化。
