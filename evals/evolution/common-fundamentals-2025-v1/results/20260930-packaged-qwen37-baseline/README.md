# 常见基本面问题：固定 JAR 真实基线

12 道开发/验证题全部完成，两阶段共 24 次真实模型调用。AI 逐题核查发现：两阶段的**题目必答金额和公式均为 12/12 正确**，但整篇回答核查通过的分析稿只有 **3/12**，最终回答只有 **1/12**。自行补充的数字、单位、大小关系和公司经营解释仍有错误；必答项正确不等于整篇答案正确。

这是原有 `baseline-v1` 的运行和 AI 来源核查，没有加入进化候选，不能据此宣称自进化已经改善效果。核查工作已由 Agent 完成，不要求用户代做逐题核对；人工独立验收、正式质量门禁和发布授权均未宣称完成。

## 数据与核查口径

题目和可见证据以 [cases.jsonl](../../cases.jsonl) 为准；答案、公式及单位见 [核对清单](../../acceptance-preparation/gold-review.md)。本次运行 MSFT、WMT、GOOGL、COST 各三题，覆盖增长质量、现金流覆盖和期末流动性。AAPL、AMZN 的六道保留题未调用模型。

每份回答分别检查必答事实、派生计算、问题要求、证据支持和额外错误。一般条件性解释不自动算错；把未给出的公司业务原因、投资目的、回款能力或未来偿债保证写成已证实事实，则不能通过。`coverageComplete` 也包含题目明示的有限度结论要求，不只是是否列出数字。AI 评审不是正式人工标签。

| 核查项目 | 分析稿 | 最终回答 |
|---|---:|---:|
| 实际执行完成 | 12/12 | 12/12 |
| 必答金额正确 | 12/12 | 12/12 |
| 必答派生计算正确 | 12/12 | 12/12 |

详细原句和逐项判断保存在 [assessment.json](assessment.json)，原始请求及回答保存在 [responses.jsonl](responses.jsonl)。不支持的解释不一定在现实中为假，但本题证据不足以确认它；下列数值错误则可直接复算。

## 具体发现

最明显的错误来自沃尔玛流动性最终回答：它写“经营与融资租赁义务（长短期合计超1.5万亿美元级别，短期约15亿美元）”。[本题报表](../../sources/wmt-liquidity.txt) 中四项合计为 `1499 + 800 + 12825 + 5923 = 21047` 百万美元，即 **210.47 亿美元**；短期为 **22.99 亿美元**。分析稿先漏算长期融资租赁，最终稿又放大了金额数量级。

| 题目 | 分析稿 | 最终回答 | 主要发现 |
|---|---|---|---|
| MSFT 增长 | 有问题 | 有问题 | 额外成本同比写 18.4%，应为约 18.5%；最终稿从合并报表推断云/AI 需求及业务组合变化。 |
| MSFT 现金流 | 有问题 | 有问题 | 从 PP&E 支出总额确认数据中心、服务器及 AI 扩张投向，缺少分项依据。 |
| MSFT 流动性 | 有问题 | 有问题 | 将递延收入视作无须消耗现金的负债，推导出过强的实际偿债安全结论。 |
| WMT 增长 | 通过 | 通过 | 利润率解释可由表内毛利与费用结构支持。 |
| WMT 现金流 | 通过 | 有问题 | 分析稿保留投向缺口，最终稿补成具体投资投向及股东回报能力判断。 |
| WMT 流动性 | 有问题 | 有问题 | 租赁负债漏项和严重单位/数量级错误；周转、议价与实际偿债判断缺来源。 |
| GOOGL 增长 | 有问题 | 有问题 | 从费用增长推断技术投入原因；最终稿把其他收益定性为非经常性投资收益，缺构成资料。 |
| GOOGL 现金流 | 通过 | 有问题 | 最终稿把资本开支上升与回购下降的同时发生写成确定因果。 |
| GOOGL 流动性 | 有问题 | 有问题 | 额外债务增长写超过 3.4 倍，实际约 3.277 倍；最终稿另断言无短期刚性借款。 |
| COST 增长 | 有问题 | 有问题 | 分析稿写 10.25%“低于”8.17%，并误判会员费占比方向；最终稿从收入增长确认拓客、留存能力。 |
| COST 现金流 | 有问题 | 有问题 | 将现金覆盖解释为管理纪律，并断言不会影响既定开店计划，缺预算或计划证据。 |
| COST 流动性 | 有问题 | 有问题 | 仅比较现金和非流动长期债就确认净现金；将其余负债全称无息，并作出绝对偿债保证。 |

这轮结果支持两个后续验证方向：对自行补充的指标同样复算、核对科目和单位；让最终整合保留分析稿的假设和资料缺口。V1 的最终回答提示词保持固定，候选能否改善最终输出仍需配对实验验证。

## 实际运行和用量

实际两阶段模型均为 `qwen3.7-plus`，温度 0.7，输出上限 4096；评测单阶段上限 120 秒，HTTP 读取上限 `PT2M`，重试次数 1。运行配置权威记录为 [runtime.json](runtime.json)；本次没有修改日常服务的超时或模型配置。

| 项目 | 分析稿 | 最终回答 |
|---|---:|---:|
| 耗时中位数 | 44.8 秒 | 43.2 秒 |
| 最长耗时 | 57.1 秒 | 53.3 秒 |
| 输入 tokens | 26,848 | 46,324 |
| 输出 tokens | 31,349 | 30,136 |
| 总 tokens | 58,197 | 76,460 |

合计 **134,657 tokens**。每次调用均有一份供应商累计用量快照，没有逐 chunk 累加。费用未定价，不能填写零费用，也不将这些 token 当作账单。先前失败尝试的未知用量未被折算成零。

所有分析稿耗时都超过 30 秒，因此本次使用的 120 秒评测上限不能证明原有 30 秒分析等待配置足够。最终流式回答也超过 30 秒，但这不等于已经证明日常服务的流式回答会按 30 秒失败；这里记录的是组件回放耗时。

## 运行身份与验证边界

运行经 `PropertiesLauncher` 加载固定 Spring Boot JAR；[build.json](build.json) 绑定 Git 基点、工作区快照和实际 JAR 哈希。14 个关键生产类来源检查通过，运行身份为 `VERIFIED_ARTIFACT / CODE_SOURCE_FILE`。外部测试驱动和四个 JUnit 依赖另记在 [driver-dependencies.json](driver-dependencies.json)，没有算入生产 JAR 哈希，也未将 `target/classes` 放入启动 classpath。[launch.args](launch.args) 保留本机启动参数，不含密钥。

Java 进程正常退出，12 个登记 run ID 均完成。现有回放校验、每题运行上下文/构建绑定、实际模型与单次供应商用量检查均通过。[baseline-report.json](baseline-report.json) 中的 `PASS` 是执行契约通过，正式 `answer_quality` 仍为 `NO_DATA`；其中时间是对已保存响应做校验的时间，不是额外模型调用。

本次修复了共享 `Coordinator` 对流式累计 usage 重复上报的问题：流完成、失败或取消时只记录最后一份快照；没有快照则记录 `NO_DATA`。17 项相关回归和 2 项打包入口检查通过。实际新运行的 24 份阶段记录均满足一次调用一份 usage，原始旧回答和旧记录未改写。

本次是固定证据的真实两阶段组件运行，未启动完整业务应用，不证明 HTTP 鉴权、操作系统权限隔离、生产存储不变或正式发布。仅四个发行人、每题一次，不能据此推断全市场效果或统计显著改善。保留的 [上一轮基线](../20260930-qwen37-baseline/README.md) 没有相同的打包身份，不作为本轮正式候选配对结果。
