# 业务 Agent 批量学习验证

本轮完成了真实经验生成和候选筛选：两组已确认的方法错误同时进入生成，一组产生候选；该候选在原错题和两个对照题中通过。但完整开发集的最终回答通过数从 **7/10 降至 5/10**，候选未满足事前登记的完整执行条件，**未选用、未上线，也未进入新公司迁移测试**。本轮没有证明稳定的最终答案收益。

机器可读结果与制品哈希以 [result.json](result.json) 为准；[汇总脚本](summarize_results.py)只聚合已有复核，不调用模型或自行赋予语义分数。[独立统计与绑定审计](final-result-audit.json)通过，确认题目映射、分母、制品哈希与用量一致。

## 范围与固定条件

- [计划](plan.json)、[逐阶段复核规则](review-policy.json)、10 道开发题及其标准答案在调用前冻结；其中 6 道沿用原开发题，4 道为同公司财报的综合题。12 道新公司 VALIDATION 题没有调用，也没有进入经验生成输入。
- 固定 JAR 调用实际业务分析与最终整合组件。两阶段实际配置均为 `qwen3.8-max`、temperature `0.7`、输出上限 `4096`、thinking budget `32768`、阶段期限 `300s`；运行清单的同步 HTTP 客户端设置记录 read timeout 为 `300s`，该记录不单独证明流式 WebClient 的读超时值。没有为制造错误降低模型配置，没有自动重试。
- 采用冻结的基本面四维标准、题目必答项、原始来源与 Decimal 核验，独立复核分析稿和最终回答。两个拟学习错误均经过第二次来源复核。复核属于 **AI 来源核查**，不是人工验收，也不是普通回答评测 Agent 准确率的新校准。
- 这是固定证据组件回放，不覆盖在线检索、RAG、用户记忆或完整服务部署。驻留服务未重启，正式发布资格仍为 `NO_DATA`。

## 执行故障与用量

[基线执行审计](development-execution-audit.json)和[候选执行审计](candidate-dev-execution-audit.json)均未发现登记、来源、JAR 或参数绑定错误；执行失败与绑定错误分别记录。

候选 02、04 的分析稿已完成，最终阶段分别运行约 92 秒、82 秒后失败。[02 日志](raw-candidate-dev-02.log)与[04 日志](raw-candidate-dev-04.log)记录了 HTTP `200 OK` 后的 `PrematureCloseException: Connection prematurely closed DURING response`。这是响应未完整接收，不是 300 秒阶段期限触发；现有证据无法区分服务端、网络或客户端连接层的具体原因，也不能证明由经验引起。

进一步沿调用代码核查，分析阶段由 [FundamentalsAgent](../../../stocksage-backend/src/main/java/com/stocksage/agent/FundamentalsAgent.java) 使用非流式 `.call().chatResponse()` 等待完整响应；[EvolutionReplayService](../../../stocksage-backend/src/main/java/com/stocksage/evolution/EvolutionReplayService.java) 的 `future.get(timeoutSeconds, ...)` 到期后取消本地任务并记录 `TIMEOUT`。候选 08、09、10 分别在 300.005、300.010、300.005 秒触发该路径；这证明本地等待期限耗尽，不证明远端已经停止生成。非流式记录没有逐段到达时间，无法从这些失败响应拆分服务端排队、推理和传输耗时。

08、10 在未加经验的基线中也超时；09 基线已耗时 276.307 秒。经验导致更多计算是待验证的耗时贡献：例如 05 分析耗时从 172.325 增至 244.972 秒，草稿也变长，但另有题目变快，所以不能将所有耗时变化都归因于经验。实际思考上限为 32768，不等于每次都用满；失败调用没有完整用量。阿里云的[深度思考说明](https://help.aliyun.com/zh/model-studio/deep-thinking)说明推理会增加等待时间，并说明流式可显示生成进展；仅改流式不会消除本地 300 秒整阶段期限。

最终阶段已经是流式。[OrdinaryAnswerReplayService](../../../stocksage-backend/src/main/java/com/stocksage/conversation/OrdinaryAnswerReplayService.java)逐段保留正文，异常时不会主动清空；两次空答案说明没有正文传到该层，不能据此断言没有思考片段或网络数据。当前记录未保存首段/最后一段到达时间或供应商请求 ID，无法进一步追溯关闭连接的一端。本轮未经过前端 SSE 或在线 RAG，不能把这两次错误归因于浏览器等待期限或检索入库。

最终阶段的 300 秒期限独立起算，没有继承分析阶段的剩余时间；运行器也没有对子进程设置这个时长的终止计时器。记录中的 `httpTransport.readTimeout=PT5M` 来自同步客户端的 `ClientHttpRequestFactorySettings`，流式 WebClient 的实际传输设置尚未单独核验。两次异常不是本地最终阶段的 `TIMEOUT`，也没有证据显示并发限流或任务取消先于连接关闭。

本轮共 **35 次业务模型调用、2 次经验生成调用**；供应商已报告 **329909 tokens**。另有 **7 次业务调用用量未知**，不能按零计；金额成本未配置，不作估算。筛选三题已包含在候选总数中，没有再次相加。上述用量不含 Codex 来源复核的用量。

## 已定位的优化点

1. **收窄经验操作。** 原错误只是“可计算却声称缺失”，生成器却要求遍历并计算所有可还原明细。本次错题分析稿从 3194 增至 5888 字符，虽然纠错成功，却增加了无关计算与输出。下一版应只在准备声明某项缺失时核查相关科目，不把局部纠错扩成全表任务。
2. **精简模型可见的学习输入。** 当前请求包含整份双阶段 Trace 及重复 Prompt/证据。[静态核对](generation-input-diagnostic.json)显示，仅保留问题、原方法、分析稿、分析证据及已核查反馈，可减少约 78%–79% 的输入字符；审计原件仍完整保留。这尚未实施或实测，不能宣称能解决本次 JSON 退化。
3. **分别处理生成与传输稳定性。** 生成器的不完整 JSON、分析超时、最终回答断流属于三个不同故障。下一次先用新登记的协议验证上述精简与收窄，再结合原始连接记录定位断流；不能继续叠加经验或把执行失败当作方法错误学习。

原始冻结实验、失败调用和标准均保留。以上是本轮边界内的结果，不是生产部署验收或自进化整体完成声明。
