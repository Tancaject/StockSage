# 超时与断流根因调查

## 结论与证据边界

**两次历史断流存在共同的本机睡眠及网络重建事件；分析超时另有已复现的长推理路径。** 固定证据对照显示，当前高推理力度下，模型可以持续收发数据但无法在 300 秒内完成分析。新增经验还扩大了计算和报告范围。本次只诊断原因，没有激活经验、修改生产预算或重启服务。

本报告是[上一轮调查](../model-stream-20261002/RESULTS.md)的后续。原批次、旧结果和冻结输入保持不变。机器结果见 [result.json](result.json)，运行前登记的条件见 [plan.json](plan.json)。

## 断流：自动睡眠中断本机网络

Windows 原始事件与原应用日志能对齐到同一个窗口，以下均为 2026-10-02、UTC+08：

| 事件 | 时间 |
|---|---|
| 两个最终回答开始调用模型 | 21:42:54.034、21:43:17.121 |
| 系统因 `System Idle` 自动睡眠 | 21:43:36.029 |
| WLAN 安全连接停止 | 21:43:38.031 |
| Wi-Fi 恢复、Mihomo 网络重新连接 | 21:44:25 附近 |
| 系统记录的唤醒时间 | 21:44:25.927 |
| 两个请求报告响应途中断开 | 21:44:26.298、21:44:38.758 |

两条已建立的 HTTP 200 响应均跨越约 49.9 秒睡眠窗口，分别在唤醒后约 0.37 秒、12.83 秒报告 `PrematureCloseException DURING response`，未达到应用的 300 秒期限。**本机在流传输期间自动睡眠、无线网络停止并重建，是已找到的具体共同中断原因。** 这不需要依靠新请求是否成功来猜测。

事件标识、原日志链接、时钟校正注意事项和读取边界见 [network-findings.json](network-findings.json)。没有历史抓包或代理连接跟踪，不能追认单个 TCP FIN/RST 的发送方，也不排除额外远端条件；本报告不把错误归咎于供应商。

原 08/09/10 三次分析都在唤醒后才开始，各自窗口没有记录新的睡眠或网卡切换。它们在本地截止附近被中断，原非流式记录没有推理、排队和首字节时序，不能反推每条历史请求的内部过程。21:47:30 的 UDP 端口耗尽告警也不足以证明 HTTPS 请求的故障原因。详见 [analysis-timeout-environment.json](analysis-timeout-environment.json)。

## 超时：高推理力度与整段期限不匹配

使用原 PEP 单季现金流问题、原可见证据和原系统消息。三个请求依次 B→A→C 执行，各一次，不重试、不并发；模型都是 `qwen3.8-max`，温度 0.7，正文上限 4096，仅本次诊断延长期限至 600 秒。

| 组别 | 新增经验 | 推理预算 | 首正文 | 总耗时 | 推理 tokens | 终止情况 |
|---|---|---:|---:|---:|---:|---|
| [B](B-candidate-medium/result.json) | 有 | 8192 | 69.516 秒 | 143.172 秒 | 3288 | `stop`，正文结束 |
| [A](A-candidate-xhigh/result.json) | 有 | 32768 | 388.672 秒 | 484.094 秒 | 13988 | `length`，正文截断 |
| [C](C-baseline-xhigh/result.json) | 无 | 32768 | 297.625 秒 | 356.156 秒 | 11276 | `stop`，正文结束 |

三组均约 1 秒收到首数据，整个流最大事件间隔均不足 1.6 秒。A 在生产截止时间之后才开始正文；C 虽在截止前约 2.4 秒开始正文，但完整分析仍需 356 秒。分析阶段等待完整回答，因此两组都不能满足 300 秒整段期限。固定输入已经包含源证据，复现期间没有调用 RAG 或工具检索。

这里有一个影响配置含义的事实：[阿里云 Chat Completions 文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)规定，Qwen3.8-Max 的 `thinking_budget` 同时映射推理力度：8192 属于 medium，32768 属于 xhigh；`max_tokens` 只约束正文，不包含推理。因而此前 4096 的正文上限没有约束长推理；A/B 同时改变了预算和力度，不能解释成纯 token 截断实验。

A/B 的实际消息完全相同，唯一请求参数差异是推理预算。A/C 的用户消息完全相同，系统消息仅增加一条 604 字符经验。A 在本次比 C 晚约 91 秒开始正文、总耗时多约 128 秒；但每组只有一次，采样、调用时间和供应商负载没有消除，不能把差值当成稳定的经验成本或普遍收益。去掉经验仍超时，也证明经验不是唯一解释。

## 新增经验为何扩大工作量

经验本意是避免“明明能从累计报表还原，却说数据缺失”。实际生成的操作却要求：

> 对同一张表内所有可还原的明细行……逐一做差值计算。

原问题只需要指定的单季指标及三个经营项目方向；用户消息还要求不扩写无关指标。该经验把一次有针对性的缺口检查扩大成全表计算。A 的可见答案增加了经营和投资明细附录，并最终在来源行中间截断。

保存的推理记录仅用于本地诊断，不在报告中展开。A 至少三次计算或重列经营明细、至少三轮规划报告，并反复检查期间与缺失行；没有新增源证据或工具调用。C 也至少三轮重复核心计算和报告规划，但没有 A 的全表附录。两组最终都转入正文，所以这是重复工作和长推理的证据，不能称为固定文本无限循环或线程死锁，也不能把重复推理归为经验独有的问题。各组的高层检查结论见对应 `source-review.json`。

## 质量不能让位于速度

复核沿用原冻结的 gold 和 review-policy，同时检查新增的重要主张，不另造评分标准：

- [B 的 AI 来源核查](B-candidate-medium/source-review.json)为 **FAIL**。六项必需数值正确，但额外明细的勾稽声明不成立，费用被混称现金支出，累计召回数据被用于单季判断。速度提高没有证明质量保持。
- [A 的 AI 来源核查](A-candidate-xhigh/source-review.json)为 **INCOMPLETE**。收到的核心数值和已核验明细未发现确定算术错误，但正文被截断，不能记完整通过。预登记的“A 超过 300 秒后自然 `stop` 完成”条件**未满足**；只证实推理自行收束，随后正文触及长度上限。
- [C 的 AI 来源核查](C-baseline-xhigh/source-review.json)为 **PASS**：必需数值、问题要求与额外重要主张通过原标准，且没有 A 的全表附录；但完整阶段仍超过原期限。`stop` 与语义通过分别检查，不能混为一项。

上述是单个问题的分析阶段诊断，没有重跑最终整合、迁移集或发布验收，不能据此计算整个 Agent 的正确率。

## 已做处理与下一步

本次 Python 诊断在请求期间使用 Windows 线程级 `SetThreadExecutionState` 阻止自动空闲睡眠，三个调用结束时均恢复原状态；没有修改系统电源方案。该调用的边界见 [Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)。它不覆盖手动睡眠，也尚未接入普通服务或完整批量评测入口。Python 未显式使用 HTTP 代理，但没有证明流量绕过系统 TUN/VPN。

针对已有证据，后续修正顺序是：

1. 长评测任务运行期间保持宿主机唤醒，并在结束时恢复；本机承载服务时同样需要宿主机持续运行。
2. 把未发布经验收窄为：只核对用户所需、或即将声称缺失的项目能否还原；删除全表计算要求。
3. 以收窄后的同证据问题比较分析阶段的推理力度，联合检查完整性、正确性和耗时，再决定默认值。单纯延长期限、加重试或全面降低预算都没有得到本次质量证据支持。

本次实际调用 3 次，用量都已返回；精确合计及文件绑定以 [result.json](result.json) 为准。本轮没有新增业务代码变更；前轮的任务取消、等待阶段提示、半截回答保留和安全传输日志仍以原报告的局部验证为准，没有在线部署验收。

输入、请求差异、原冻结产物及复核文件的绑定检查见 [verification.json](verification.json)。诊断脚本 `--self-check`、本次相关文档的本地链接、凭据模式检查和相关 `git diff --check` 均通过；未重跑无关业务测试。
