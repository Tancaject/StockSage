# 模型超时与断流排查

本轮复现了“连接持续传输，但分析一直没有进入正文”的超时；原先两次最终回答断流没有再次复现，关闭连接的一端仍未确定。修复了另外两个会放大体验问题的确定缺陷：普通分析取消没有中断真实工作任务，以及前端报错覆盖已收到的正文。

统计与制品哈希见 [result.json](result.json)，验证记录见 [verification.json](verification.json)。这是三个新登记、各一次的传输诊断，不改写原批量学习实验，不评价本轮答案质量，也不授权经验发布。

## 超时：本次模型持续推理到本地期限

[直接流式复现](direct-analysis-09/result.json)使用原候选开发题 09 的同一份分析输入，仍为 qwen3.8-max、temperature 0.7、正文上限 4096、thinking budget 32768、总期限 300 秒；改变的是 Python 直连及流式接收，用于观察实际到达过程。

- 0.953 秒收到第一个思考事件，299.984 秒仍有事件到达。
- 共收到 3618 个事件、37290 个思考字符，正文为零；最长事件间隔约 1.328 秒。
- 在本地 300 秒期限结束；供应商没有返回最终用量，因此记为未知。字符数不是 token 数，思考内容没有写入诊断文件。

这次超时发生时连接没有长时间静默，持续思考消耗了等待窗口。原非流式失败没有逐段记录，因此不能倒推所有历史超时都具有相同过程，也不能判断模型用了多少思考 token 或是否陷入重复推理。改成流式能观察活动，不会自动缩短思考总时长。

[Java 传输日志](java-final-02.log)记录了供应商请求标识、200 状态、首数据约 1.750 秒、末数据约 71.326 秒、830 个数据块及 223118 字节。SDK 在完成标记后取消上游，日志为 `termination=cancel, errorType=NONE`，不能据此误判失败。

两次新采样成功只表示没有复现，不能证明历史断流已修复。历史错误确实是 HTTP 200 后的 `PrematureCloseException`；源码及实际依赖核查没有发现会在 82/92 秒触发的本地计时器，也没有证据支持取消互相干扰或长期连接池积累。后续 Windows 事件核查找到两次断流共同的本机睡眠及网络重建窗口，见[根因调查](../model-root-cause-20261002/RESULTS.md)；本轮原始 `result.json` 保留当时尚未定位的结论。

## 已修复与验证

- **真实取消工作任务。** `ToolPrefetchService` 用同一执行器上的 `FutureTask` 替代 `CompletableFuture.supplyAsync`。超时取消可中断真实工作线程；调用者中断时恢复中断位、结束准备流程，不继续最终生成。这不保证远端供应商已停止推理或计费。
- **显示实际阶段。** 证据取得、分析已提交后显示等待领域分析的提示，避免整个分析期间仍停留在获取证据的描述。
- **保留半截回答。** 普通聊天的服务端错误和连接错误均保留已收到的正文，前置未完成及重试提示；复制、导出保留该标记，界面不再把失败输出标为已形成结论。没有正文时保留错误展示。没有增加半截回答的后端持久化，刷新后的恢复不在本次保证范围内。
- **记录可追查的传输信息。** 模型 WebClient 每次 HTTP 尝试记录安全请求标识、状态、首末数据时间、数据量、终态和根异常类型，不记录正文、思考或凭据。已观察到的运输错误优先于异常处理过程中伴随的取消信号。

修改前 fast harness 通过；修改后的相关后端检查共 32 项通过，覆盖真实线程中断、分段 HTTP 提前关闭、原取消链及模型选项。前端现有 targeted suite 两项通过，覆盖两种错误入口及有/无正文；构建通过。以上为本地组件与处理函数验证，没有完整浏览器/在线服务部署验收。驻留服务未重启，未提交或推送。

## 用量与后续范围

本轮实际调用 3 次，没有自动重试；两次完成调用已知合计 17997 tokens，另一次用量未知，不按零计。未更换默认模型、降低思考预算、提高期限、自动重试或激活学习候选。

长等待仍需单独验证准确率与耗时的取舍：分析和最终整合应分别评估所需思考预算；候选经验要求额外全表计算的问题仍按原学习报告收窄后再测。当前证据不支持直接降低整个系统预算并宣称质量不变。若断流再发生，可使用新增请求标识和传输时序核对供应商侧记录。
